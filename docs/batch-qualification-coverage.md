# Batch qualification coverage follow-up

This follow-up addresses source conditions omitted from otherwise complete model
disposition maps. It does not modify saved reports, candidate profiles, CVs or
SkillsBank data and does not deploy or rerun a production batch.

## Coverage and classification boundaries

* Qualification prose in an explicit mandatory/preferred section needs an
  assessment or unresolved-source review. Labeling it as context, a duty, or an
  unweighted competency cannot by itself establish reliable coverage. This
  includes education, soft traits and nominal skill/practice conditions,
  not just a fixed list of technology names.
* Bare product tags retain the existing advisory response-grammar
  contract. Actual portal tags/levels, administrative text and offered benefits
  are not invented mandatory qualifications. Working arrangements retain their
  separate personal-confirmation path; technical evidence cannot prove consent.
* Explicit Polish proficiency modifiers, education clauses, mandatory AI
  proficiency and English-level predicates remain assessable even when their
  inherited section is wrong. A colon after `Must have ...` does not erase the
  condition before a language/tool list.
* A leading `Docenimy doświadczenie ...`, `Dodatkowym atutem będzie ...`, or
  `Nice to have: ...` marks a preference even inside a requirements section.
  The independent final validator enforces this on older/provider output too,
  not only compact row normalization. A trailing preference does not downgrade
  the main mandatory condition.
* An inherited stack category is not a blanket metadata exemption for explicit
  candidate predicates. Only actual tag/level metadata receives that exemption.
* Strict qualification headings terminate a previous stack category; `Scope of
  Services` terminates a preceding preference section and starts duties. Marketing
  headings are not candidate capabilities.

All status/evidence, AND/OR, negation, language-level and tenure validators remain
active. The correction does not invent missing assessments or evidence and does
not turn model failures into successful analyses. Recovery uses the existing
bounded attempt budget; persistent omissions still fail closed. There are no new
dependencies, model downloads, external calls or configuration requirements.

## Verification

Fixtures use a fictional company and an empty fictional candidate profile.
An isolated archive of `ea1b9d9` with the initial 100-case regression file produced
**95 failures and 5 passes**. The same file subsequently passed all 100 cases;
additional negative/compatibility cases were then added. This measures targeted
regression reproduction, not general model accuracy.

The final focused run passed **546 tests** across the two new regression files
and existing source layouts, source coverage, metadata revalidation, token budgets,
indexed recovery, analysis graph, role assessment, LLM-first analysis and
qualification/evidence guards. The two new files contribute **126 cases** (102
coverage cases and 24 heading cases). Ruff, environment conformity, dependency
consistency and diff checks pass.

The full suite ran alone and completed with **2230 passed, 1 skipped, 13 warnings
in 1763.68 seconds (29:23)**. The optional real-embedding test remains opt-in;
warnings are third-party LangSmith deprecations, with an additional pytest-asyncio
configuration warning at startup. Previous full-suite counts in the
requirement-audit document are not validation of this follow-up. Tests use the
pinned Python 3.14 environment and mocked providers.

## Remaining limits

Section hints still cannot prove arbitrary semantic equivalence or candidate
competence. Unknown layouts and compound conditions may require explicit review.
Passing these regressions is not a claim that every saved CV is accurate. Saved
reports require fresh analysis after a separately authorized deployment; simply
reloading an old report will not apply the correction. Failed batch entries are
not silently retried or admitted by weakening validation.
